# Commit Guidelines
Every commit must keep `lake build` passing, with no `sorry` warnings, and `lake lint` must pass: CI runs both. `scripts/ci-local.sh` runs everything CI runs, after one build and in parallel, and first checks that no added line in a `.lean` file is longer than 100 characters.

Commit any changes made at logical intervals (e.g., don't commit incomplete features); keep the commit messages clear and concise. Use this format:

```
<type>(<scope>): <short description>
```

- `type`: what kind of change (see below)
- `scope`: optional, the affected module or file (e.g. `parser`, `lakefile`, `tactics`)
- `description`: imperative, lowercase, no trailing period

## Types

| Type | When to use |
|------|-------------|
| `init` | Initial commit |
| `feat` | New feature or tactic added |
| `fix` | Bug or proof error fixed |
| `refactor` | Code restructured without changing behavior |
| `style` | Formatting, whitespace, or naming (no logic change) |
| `docs` | Docstrings, comments, or README updated |
| `test` | `#check`, `#eval`, `example`, or spec added/updated |
| `chore` | Dependency update, config change |
| `toolchain` | Toolchain bump |
| `perf` | Proof or computation made more efficient |
| `ci` | GitHub Actions or CI pipeline changes |
| `build` | `lakefile.toml`, or build system changes |
| `revert` | Reverts a previous commit |

## Scopes

| Scope | Refers to |
|-------|-----------|
| `lakefile` | `lakefile.toml` changes |
| `tactics` | Custom tactic definitions |
| `parser` | Syntax or parser extensions |
| `notation` | Custom notation definitions |
| `<Module>` | Some update to that module, like `SKIConv` or `Halt` |

One logical change per commit; if you find yourself writing "and" in the message, consider splitting it.
- Scope to the module name when possible: `feat(SKIConv): ...`
- Never commit directly to `main`. Commit to a new branch.

# Layout

Each problem has a folder under `DiagonaLean/`: `Basic.lean` states it, `Reductions/` holds the reductions to it, `SynthHardness.lean` the synthetic results, and `Undecidable.lean` the undecidability results (`Halt`, where every reduction starts, has no `Reductions/`). `Reductions/` holds only files `Y_to_X.lean` and a README: the functions, their correctness and their computability, including the reduction from canonical machines (`HaltCanon_to_X.lean`) and the constructions it is built from. `SynthHardness.lean` holds the packaged synthetic reductions from the halting problem (`X.synthFromHalt : SynthHaltReduction X.DecisionProblem`, `X.synthComplFromHalt`, and their forms over other alphabets), and nothing else. `Undecidable.lean` holds the proved layer: the halting reduction `X.fromHalt : HaltReduction X.DecisionProblem` and the line `halt_results X.DecisionProblem from X.fromHalt`, which states `X.haltHard`, `X.not_computablePred : Undecidable X.DecisionProblem` and `X.not_machineDecidable` (no hand-written wrappers). When the reduction takes constants that exist only classically, such as a race program, it is `X.fromHaltWith c … : HaltReduction X.DecisionProblem`, and `halt_results` takes the proof of `HaltHard` that obtains them instead (`SKIConv/Undecidable.lean`). A problem with no proved halting reduction states `Undecidable` (`¬ ComputablePred`) or `¬ MachineDecidable enc` there by the route it has (`not_computablePred_of_reduces`, `ProofRace`). `AlphabetLift.lean` moves the problem between alphabets with the codes of `Foundations/Codes/`: encoding an instance by a code preserves and reflects its answer, so the problem is a `CodeFunctor`, and the tactic `code_lift` lifts `SynthHaltReduction`, `HaltReduction`, `¬ ComputablePred` and `¬ MachineDecidable` from one alphabet to every alphabet with two distinct letters. `SynthHardness.lean` and `Undecidable.lean` import `AlphabetLift.lean`, not the reverse.

`Basic.lean` is where a reader audits what a problem means, so it imports only Mathlib, Cslib, other `Basic.lean` files and definition-only `Foundations/` files (`Foundations/Rewriting/SRS.lean`, `Foundations/CombinatoryLogic/Conv.lean`), never proof machinery. It states the problem curried first, named for the problem (`SemiThue.WordProblem R u v`, `SKIConv.Convertible x y`), with one-step relations as inductives and closures from Mathlib (`ReflTransGen`, `EqvGen`, `Join`), never hand-rolled. Then, in one line, the one-argument `DecisionProblem` on instances that the reductions and the computability statements use, followed by `@[simp] theorem decisionProblem_mk … := Iff.rfl` (its curried reading) and, for a rewriting problem, a theorem stating it in Mathlib's and Cslib's terms by `Iff.rfl` (`wordProblem_iff`, `convertible_iff`). These statements are pinned in `scripts/HeadlineTest.lean`. Results are stated on the one-argument problem only: a partially applied curried problem type-checks as a different claim. Namespaces follow the role of their file (`X.Reduction` in `Reductions/`, `X.AlphabetLift`, `X` for results). The skill file `.claude/skills/diagonalean/SKILL.md` (§2) has the full rules and the reasons for them. Results that relate several problems, such as that two problems have the same many-one degree, live in `Degrees/` (`Degrees/Rewriting.lean`); a problem folder never imports another problem's results to state them. Problems that come from one larger result share a folder with one subfolder per problem, as in `KAComm/`, and their namespaces follow the path (`DiagonaLean.KAComm.TermEq`). Code that only one problem uses lives in that problem's folder, as `KAComm/KleeneAlgebra/` does; once several problems use it, it moves to `Foundations/`, as the normalisation of Turing machines (`Foundations/Computability/Normalize/`) did. `Foundations/` holds general results and may depend, even through other imports, only on `Foundations`, `Synthetic` and `Halt`; `scripts/CheckLayering.lean` checks this in CI.

# Reductions

`SynthHaltReduction p` is the type `HaltProblem ⪯_s p`, so an undecidability result is a definition whose value is the reduction, and composing results composes their functions. Lean's logic is classical, so a term of that type exists for every `p` with a positive and a negative instance: the case split `if HaltProblem x then a else b`. That case split is not a program, and Lean refuses to compile it. So a result means something because it is a definition that Lean compiles, and CI checks this with `#check_reductions` (`DiagonaLean/Synthetic/ReductionCheck.lean`). It enforces conventions 2–4, 10 and the first half of 11, `scripts/CheckMetaprograms.lean` enforces convention 9 and the second half of 11, and the tests `scripts/ReservedWordsTest.lean` and `scripts/HeadlineTest.lean` enforce the rest of 11 and 12. Conventions 1 and 5–7 are what let it see a result at all, and only review enforces them: a result that steps outside them is not checked, even if CI passes.

## Writing an undecidability result

[KEY-THEOREMS.md](KEY-THEOREMS.md) lists the notions, theorems and tactics you will need, and the pitfalls that cost time.

1. **State it with the library's notions.** Use `SynthHaltReduction p` or `p ⪯_s q`, or a definition that unfolds to one of them; for the proved layer `HaltReduction p` (from `HaltCanon`) and `HaltHard p`; and state a result about machines as `¬ MachineDecidable enc p`. The check does not see a home-made statement such as `¬ ∃ M, decides M p` or a new reduction structure. Reduce from the library's `HaltProblem` or `PCP.DecisionProblem`, not from a local copy.
2. **Every result is a `def` that Lean compiles.** Build the reduction function as a named `def` in `Reductions/Y_to_X.lean`, with its correctness `src_reducesto_foo_spec : Src ⪯_s[srcToFoo] Foo`, and state the result as a `def` built from the two: `def Foo.synthFromHalt : SynthHaltReduction Foo := by synth_reduce_from (PCP.synthFromHaltOver b0 b1 hne) with srcToFoo using src_reducesto_foo_spec` (or `reduce_from_pcp over_letters b0 b1 with …`), and in the proved layer `def Foo.fromHalt : HaltReduction Foo := by hard_reduce_from (PCP.fromHaltOver b0 b1 hne) with srcToFoo using src_reducesto_foo_spec`, then `halt_results Foo from Foo.fromHalt`. Tag a parameter-free reduction with `@[undecReduction]` and a theorem `¬ ComputablePred P` with `@[undecHardness]` so that `undec from` can use them (see the README); `halt_results` does this for the theorems it states. A proof in the library names its route, `reduce_from h via r₁, via r₂, …`, rather than searching for one with `undec from P`, `undec?` or `reduction_path`, whose result depends on what is imported; `undec?` prints the script to paste, and `scripts/CheckMetaprograms.lean` (its `search` rule) rejects the search forms in the library. Use the library's tactic for every job it covers (reductions, `upgrade`, `code_lift`, `halt_results`, `fun_prop`, `derive_primrec`, `primrec_rec`, `derive_primcodable`); when one fails on a case it should cover, fix it with a regression test or report the gap, rather than writing the proof around it. Do not define a bundled link `Foo.synthFromSrc := ⟨srcToFoo, spec⟩` only for the tactics; define one only when several results compose it. Results live in the target's namespace and say what they reduce from: `Foo.synthFromHalt` for a halting reduction, `…Over b0 b1 hne` and `…Bool` for alphabet variants; `synth` marks a reduction whose computability is not proved (the proved versions drop it: `MPCP.fromHalt`). A second problem in one namespace takes a prefix in `halt_results` (`SemiThue.Pos.haltHard`, `EmpCFG.Code.haltHard`). `scripts/rename-packages.tsv` lists the former names; none of them has an alias: the deprecated aliases were removed on 2026-11-27, and the wrappers and bundled links deleted on 2026-11-25 never had one. It must not be `noncomputable` or `unsafe`, and must not use `implemented_by` or `extern`. If Lean asks for `noncomputable`, the reduction is not a program; fix the definition rather than adding the marker. Data obtained only classically, such as letters from `Nontrivial α` or a program code from an existential, cannot be used in a compiled definition: take it as an argument (`PCP.synthFromHaltOver b0 b1 h`, `KAComm.TermEq.synthFromHalt B C hB hC`).
3. **Never state a reduction as a proposition.** A theorem may take reductions as hypotheses, but must not claim that one exists: `Nonempty (SynthHaltReduction p)`, `∃ r : p ⪯_s q, …` or `∃ f, p ⪯_s[f] q` holds classically and says nothing, and so do the disguised forms `¬¬ Nonempty (p ⪯_s q)` and `∀ c, (p ⪯_s q → c) → c`, where the reduction is in a hypothesis of a hypothesis. That no reduction exists, `¬ Nonempty (p ⪯_s q)`, may be stated. Writing the relation out, as `∃ f, ∀ x, p x ↔ q (f x)`, is as empty, and the check cannot see it. Do not use `axiom` or `opaque` for reductions, and do not wrap a reduction in another type (an `Equiv`, a pair, a structure field or an inductive proposition), even through an alias.
4. **No escape hatches in anything a reduction depends on.** Do not use `implemented_by`, `extern`, `opaque`, `partial`, `unsafe` or `sorry` in any definition a reduction depends on, directly or indirectly. Its proofs, including the theorems they use, must not use `sorry`, an `axiom`, or `native_decide` (which trusts compiled code; use `decide`), and every `@[csimp]` lemma must be proved the same way. These let a definition compile while its logical meaning is classical, so the check walks every definition a reduction depends on. For faster code, use `@[csimp]` with a proof that the two functions are equal. For recursion, prove termination (structural recursion or `termination_by`) rather than using `partial`. Beyond reductions, every declaration of the library may depend only on `propext`, `Classical.choice` and `Quot.sound` (`scripts/CheckAxioms.lean`): no `axiom`, `sorry` or `native_decide` anywhere, including the proved layer (`HaltReduction`, `HaltHard`) and its instances. Work in progress may use `sorry` in a file listed in `sorryAllowances` (`DiagonaLean/Synthetic/AxiomCheck.lean`), with a comment saying what is missing; a declaration outside the list that uses one of its results is still reported.
5. **Put the result where CI looks.** The check covers modules under `DiagonaLean/` that the root module `DiagonaLean` imports. Import every new module from `DiagonaLean.lean`; a module left out, or a result in `scripts/` or a test file, is not checked. (`Synthetic/EvalExample.lean` is left out on purpose and contains no reductions.)

## Maintaining the check

6. **Register new reduction structures.** Add a new structure to `reductionStructs`, and a relation like `p ⪯_s[f] q` to `reductionRelations` (but not `p ⪯[f] q`, which includes a proof that `f` is computable, so its existential is Mathlib's `ManyOneReducible` and has content); otherwise the check ignores them. Definitions that unfold to an existing reduction structure, such as `SynthHaltReduction`, are found automatically.
7. **Trust packages deliberately.** `trustedPrefixes` lists the packages whose code the dependency walk does not enter: Lean, Batteries, Mathlib, Cslib and the other current dependencies. When adding a dependency, decide whether to trust it before adding it there; leave small or unaudited packages untrusted.
8. **Add every new way of cheating to the tests.** `scripts/CheckReductionsTest.lean` holds the cases the check must reject and the honest cases it must accept. Add a case there, with its expected error, together with the fix that catches it. A metaprogram goes in `scripts/metaprogram-fixture/` instead.
9. **No metaprograms that change the environment.** A `run_cmd` can add a classical reduction with `addDecl` and give it the compiled code of an honest stub; the kernel and `lean4checker` accept it, and so does `#check_reductions`, which reads the environment. `debug.skipKernelTC` adds declarations the kernel never checked. So the library does not use `run_cmd`, `#eval`, `initialize`, `debug.` options, `unsafe`, new commands, or functions such as `addDecl` and `modifyEnv`; `scripts/CheckMetaprograms.lean` rejects them outside an allowlist. The commands `register_label_attr`, `register_simp_attr` and `register_option` expand to `initialize` and count as it. It parses each file with Lean's parser, so comments and string literals never count; the rules and the allowlist are in `Synthetic/MetaprogramCheck.lean`, and `scripts/CheckMetaprogramsTest.lean` tests them. Tactics written with `elab` run arbitrary code, and review must check that they only build proofs. The allowlist names declarations, file by file, not whole files: the commands `#check_reductions` (`Synthetic/ReductionCheck.lean`), `derive_primcodable` (`Foundations/Computability/DerivePrimcodable.lean`), `derive_primrec` (`Foundations/Computability/DerivePrimrec.lean`) `halt_results` (`Foundations/Computability/HaltResults.lean`, a macro to three `theorem` commands) and `re_results` (the same file, a macro to an `instance` and a `theorem`), and their helpers, so a second command in the same file is rejected. Every new command needs an entry, a `macro` too. `initialize` is allowed in `Synthetic/Tactics/ReductionPath.lean` and `Foundations/Computability/UndecTransfer.lean`, for the tags `@[undecReduction]` and `@[undecHardness]` and the option `undec.showRoute`, which add no declarations. The last two only parse generated source text and elaborate it with `elabCommand`, as if written by hand; review must check that they stay so, since they may define a command but still may not use `addDecl`, `modifyEnv` or the other functions above.
10. **Encodings are programs.** A result about machines is only as honest as its encoding: an encoding that stores the answer in its first bit makes any predicate decidable. So in the type of every result, in the type of every constructor, and in the body of every predicate, `#check_reductions` requires the constants of each encoding to be programs, under the rules for reductions (convention 4). An encoding is an instance of `Encodable`, `Primcodable` or `Denumerable` (`encodingClasses` in `Synthetic/ReductionCheck.lean`), or an argument of a predicate whose type carries one: a function into `List Bool`, curried or not, or a structure or class with such a field or an encoding instance field. Machine-level predicates are found from their types, so a new one needs no registration. An encoding that is a bound variable, as in `∀ enc, Computable enc → ¬ MachineDecidable enc P`, needs no check. Do not build an encoding or a `Primcodable` instance with `Classical.choice`, `Classical.decPred` or a `noncomputable` definition; the check also reports classical choice in a proof argument of an encoding, although proofs carry no code. The check shows that an encoding is a program, not that it is the natural one, so a new instance with an unusual encoding still needs review.
11. **New syntax starts with a fresh token, and existing syntax keeps its meaning.** Lean resolves overlapping notation by the longest parse and reports only a tie, so `macro "¬" p:term:36 "∧" q:term:35 : term => `(True ∨ ($p ∧ $q))` silently makes every `¬ A ∧ B` state `True ∨ (A ∧ B)`. So each `term` or `command` syntax of the library must start with a token no other parser of its category starts with (for trailing syntax, the token after the left-hand side); `#check_reductions` reads the parser tables, and an exception goes in `syntaxOverlapAllowances`, with a comment. Only tactic syntax may get new `macro_rules` or `elab_rules`, `@[macro]`, `term_elab` or a `(priority := …)`: on a command or a term they can silence a check or change what a statement says, so `scripts/CheckMetaprograms.lean` (its `expander` rule) rejects them at any depth, including inside `open … in`. A word in a `syntax`, `macro`, `elab` or `notation` declaration becomes a reserved keyword, which no importing file can then use as a name; write a word that should stay a name as `&"word"`. `scripts/ReservedWordsTest.lean` reports every word-like keyword not in its `knownKeywords`, and a new command's first word goes there.
12. **Change a headline statement on purpose.** `scripts/HeadlineTest.lean` states the headline results with their exact statements, so a change that weakens one (an extra hypothesis, a weaker conclusion, another problem or encoding) fails CI although every other check passes. A deliberate change updates its `example` in the same commit, and a new headline result gets one.

## What the check guarantees

Under these conventions, every undecidability result is a program, and the function it computes when compiled is the function the proof reasons about. The check trusts that the environment it reads is the one Lean's elaborator, kernel and compiler built; convention 9 is what makes that hold. It does not prove that the function is `Computable`, and of the encoding of inputs it shows only that it is a program (convention 10), not that it is reasonable; reductions proved through `ComputesReduction` or Mathlib's `Computable` carry that guarantee themselves. The proved layer (`HaltReduction`, `HaltHard`, the registries `HaltSource`, `HaltHardFact` and `REFact`, and what `halt_results` and `re_results` state) is not walked by `#check_reductions`: the kernel checks its computability, and `scripts/CheckAxioms.lean` rules out an `axiom` or `sorry` there. Its results are still relative to the `Primcodable` instances of the instance types, so a new instance with an unusual encoding needs review.

To check locally after `lake build`, run `lake env lean scripts/CheckReductions.lean`, `lake env lean scripts/CheckReductionsTest.lean` and `lake env lean --run scripts/CheckAxioms.lean`, or `scripts/ci-local.sh` for every check CI runs.

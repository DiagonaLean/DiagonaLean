# Commit Guidelines
Every commit must keep `lake build` clear. Linting warnings are fine for now. No `sorry` warnings must be thrown.

Commit any changes made at logical intervals (e.g., don't commit incomplete features); keep the commit messages clear and concise. Follow the following format (*most of what is below this point was generated by Claude Sonnet 4.6*):

```
<type>(<scope>): <short description>
```

- `type`: what kind of change (see below)
- `scope`: optional, the affected module or file (e.g. `parser`, `lakefile`, `tactics`)
- `description`: imperative, lowercase, no trailing period

## Types

| Type | When to use |
|------|-------------|
| `init()` | Initial commit |
| `feat()` | New feature or tactic added |
| `fix()` | Bug or proof error fixed |
| `refactor()` | Code restructured without changing behavior |
| `style()` | Formatting, whitespace, or naming (no logic change) |
| `docs()` | Docstrings, comments, or README updated |
| `test()` | `#check`, `#eval`, `example`, or spec added/updated |
| `chore()` | Dependency update, config change |
| `toolchain()` | Toolchain bump |
| `perf()` | Proof or computation made more efficient |
| `ci()` | GitHub Actions or CI pipeline changes |
| `build()` | `lakefile.toml`, or build system changes |
| `revert()` | Reverts a previous commit |

## Scopes

| Scope | Refers to |
|-------|-----------|
| `lakefile` | `lakefile.lean` or `lakefile.toml` changes |
| `tactics` | Custom tactic definitions |
| `parser` | Syntax or parser extensions |
| `notation` | Custom notation definitions |
| `<Module>` | Some update to that module, like `(DiagonaLean.)Halt.Encoding` |

One logical change per commit; if you find yourself writing "and" in the message, consider splitting it.
- Scope to the Lean module name when possible: `feat(MyProject.Eval): ...`
- Never commit directly to `main`. Commit to a new branch.

# Reductions

`Undecidable p` is the type `HaltProblem ⪯ₘ p`, so an undecidability result is a definition whose value is the reduction, and composing results composes their functions. Lean's logic is classical, so a term of that type exists for every `p` with a positive and a negative instance: the case split `if HaltProblem x then a else b`. That case split is not a program, and Lean refuses to compile it. So a result means something because it is a definition that Lean compiles, and CI checks this with `#check_reductions` (`DiagonaLean/Synthetic/ReductionCheck.lean`). It enforces conventions 2–4. Conventions 1 and 5–7 are what let it see a result at all, and only review enforces them: a result that steps outside them is not checked, even if CI passes.

## Writing an undecidability result

1. **State it with the library's notions.** Use `Undecidable p`, `p ⪯ₘ q`, `SepReduces` or `InsepUndecidable`, or a definition that unfolds to one of them. The check does not see a home-made statement such as `¬ ∃ M, decides M p` or a new reduction structure. Reduce from the library's `HaltProblem` or `PCP.DecisionProblem`, not from a local copy.
2. **Every result is a `def` that Lean compiles.** Build the reduction in a named `def` in `Reductions/Y_to_X.lean`, and state the result as a `def` too: `def fooUndecidable : Undecidable Foo := undecidabilityFromReducibility pcpUndecidable' pcpReducesFoo`, or `reduceFromPCP over_letters b0 b1 via R` for reductions from PCP. Name it in lowerCamelCase, as the linter requires for definitions. It must not be `noncomputable` or `unsafe`, and must not use `implemented_by` or `extern`. If Lean asks for `noncomputable`, the reduction is not a program; fix the definition rather than adding the marker. Data obtained only classically, such as letters from `Nontrivial α` or a program code from an existential, cannot be used in a compiled definition: take it as an argument (`pcpUndecidable b0 b1 h`, `undecidableTermEq B C hB hC`).
3. **Never state a reduction as a proposition.** A theorem may take reductions as hypotheses, but its conclusion must not mention one: `Nonempty (Undecidable p)` or `∃ r : p ⪯ₘ q, …` holds classically and says nothing. Do not use `axiom` or `opaque` for reductions, and do not wrap a reduction in another type (an `Equiv`, a pair, a structure field or an inductive proposition), even through an alias.
4. **No escape hatches in anything a reduction depends on.** Do not use `implemented_by`, `extern`, `opaque`, `partial`, `unsafe` or `sorry` in any definition a reduction depends on, directly or indirectly. Its proofs, including the theorems they use, must not use `sorry`, an `axiom`, or `native_decide` (which trusts compiled code; use `decide`), and every `@[csimp]` lemma must be proved the same way. These let a definition compile while its logical meaning is classical, so the check walks every definition a reduction depends on. For faster code, use `@[csimp]` with a proof that the two functions are equal. For recursion, prove termination (structural recursion or `termination_by`) rather than using `partial`.
5. **Put the result where CI looks.** The check covers modules under `DiagonaLean/` that the root module `DiagonaLean` imports. Import every new module from `DiagonaLean.lean`; a module left out, or a result in `scripts/` or a test file, is not checked. (`Synthetic/EvalExample.lean` is left out on purpose and contains no reductions.)

## Maintaining the check

6. **Register new reduction structures.** Add a new structure to `reductionStructs`; otherwise the check ignores it. Definitions that unfold to an existing reduction structure, such as `Undecidable`, are found automatically.
7. **Trust packages deliberately.** `trustedPrefixes` lists the packages whose code the dependency walk does not enter: Lean, Batteries, Mathlib, Cslib and the other current dependencies. When adding a dependency, decide whether to trust it before adding it there; leave small or unaudited packages untrusted.
8. **Add every new way of cheating to the tests.** `scripts/CheckReductionsTest.lean` holds the cases the check must reject and the honest cases it must accept. Add a case there, with its expected error, together with the fix that catches it.

## What the check guarantees

Under these conventions, every undecidability result is a program, and the function it computes when compiled is the function the proof reasons about. The check trusts that the kernel checked every declaration; a metaprogram that adds declarations without the kernel (`debug.skipKernelTC`) is outside it, and only rechecking the library with `lean4checker` catches that. It does not prove that the function is `Computable`, and it says nothing about whether the encoding of inputs is reasonable; reductions proved through `ComputesReduction` or Mathlib's `Computable` carry that guarantee themselves.

To check locally after `lake build`, run `lake env lean scripts/CheckReductions.lean` and `lake env lean scripts/CheckReductionsTest.lean`.
